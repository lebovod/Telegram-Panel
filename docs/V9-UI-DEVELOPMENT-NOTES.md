# 天浩独家开发 V9：UI 开发笔录

更新时间：2026-08-05（Asia/Phnom_Penh）

## 本次审核标准

新版界面只按三项标准验收：

1. 实用：核心状态和异常必须在首屏看到。
2. 高效：高频操作两步内到达，工作顺序明确。
3. 简洁：删除重复入口、装饰性信息和无意义层级。

## 仓库自查结论

- 当前仓库主分支在 2026-08-05 没有今天讨论内容对应的提交。
- 原界面仍是通用 Telegram Panel 布局，导航按技术模块拆分，业务主链路不够清晰。
- 首页已有真实账号、频道、群组、任务数据读取和同步功能，本次保留这些业务逻辑并重构呈现方式。

## 今天讨论但当前仓库尚未落地的主链路事项

以下内容不能只做 UI，需要后端服务、数据库和运行环境一起实现并实测：

- [ ] 升级后旧数据、采集账号和配置的自动迁移及迁移报告。
- [ ] 后台重启后自动读取已启用采集账号 Session 并自动上线。
- [ ] 自动恢复监听来源、采集任务和发布任务；Session 有效时不重复验证码登录。
- [ ] 发布任务长时间 `queued` 的超时检测、Worker 健康检查和自动恢复。
- [ ] 发布失败时将 Telegram/API 原始错误、账号、频道、任务步骤写回数据库。
- [ ] 日志目录、控制台和页面日志三处保持一致，禁止出现“失败但无日志”。
- [ ] Bot Token 有效性、频道权限和管理员权限在任务提交前预检。
- [ ] 频道 ID、`@username`、邀请链接的统一解析与明确错误提示。
- [ ] 失败任务提供“立即重试”，并保留原任务参数和历史记录。
- [ ] 发布中心直接提供“新增发布任务”按钮，成功配置可留底复用。
- [ ] 采集、处理、发布页面统一使用相同的状态、筛选、错误详情和操作规范。

## 下一阶段实施顺序

1. 先补发布 Worker、错误回写、日志和立即重试，解决“任务不可诊断”。
2. 再实现 Session 自动恢复和任务恢复，保证后台重启后主链路不中断。
3. 然后实现旧数据迁移、配置留底和发布中心。
4. 最后统一各业务页面 UI，禁止先做装饰性功能。

## 验收底线

- 按钮必须连接真实业务动作，不能只弹提示或展示概念页面。
- 每次失败必须能看到明确原因、发生时间、执行账号、目标频道和重试入口。
- 后台重启后，应自动恢复有效 Session、监听和任务。
- 新版本升级不得静默丢失旧数据；迁移失败必须给出清单。
